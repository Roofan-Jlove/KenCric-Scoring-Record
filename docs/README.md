# KenCric Scoring Record — Documentation

Spec-Driven Development (SDD) documents for the **Cricket Scoring Book** project.

## Start here

**[`master-specification.md`](master-specification.md)** assembles all 18 documents below into one source of truth, structured in 15 sections (Product → Domain → Requirements → UX → Architecture → Data → API → Offline/Sync → Security → Testing → Acceptance Criteria → Traceability Matrix → ADRs → Glossary → Open Questions). Read it first — it is sufficient on its own to understand the whole system, and points precisely to the constituent below whenever the full detailed text is needed.

**[`ai-context-pack.md`](ai-context-pack.md)** is the condensed, rule-form version of this entire corpus for AI coding sessions — read it before writing or editing any code in this repository. It restates the Master Specification and its constituents as Project Constitution, Coding Rules, Naming Conventions, Security Rules, Testing Rules, Git Rules, Documentation Rules, Forbidden Assumptions, and a full Requirement-ID legend, with pointers back to full source text throughout.

**[`ai-development-harness.md`](ai-development-harness.md)** is the repeatable workflow that uses the Context Pack: Context → Prompt → Plan → Implement → Test → Verify → Review → Update Context, with required context files, prompt templates, a task schema, verification checks, human approval gates, a regression process, and the hard guarantee that an AI session never silently changes an approved requirement.

**[`implementation-task-backlog.md`](implementation-task-backlog.md)** breaks the Master Specification into small, dependency-ordered `TASK-####` units sized for one AI development loop each — the first concrete backlog the harness's workflow can run against. No implementation.

## Reading order

0. **Master Specification — read this first.**
1. Foundation — *what problem, for whom, and why*.
2. Discovery — *who the users are and every requirement, uniquely identified*.
3. Domain Specification — *what is true in the cricket domain and what the scoring record must contain*.
4. Domain Glossary + Formal Domain Model — *as what objects, with what identity, state, and behaviour*.
5. Software Requirements Specification — *every requirement consolidated, prioritised, traced, and given acceptance criteria*.
6. Product Roadmap — *what ships when: MVP → Version 1 → Version 2 → Future*.
7. System Architecture — *how it is built: the 4 Layers, and every architecture area from frontend to security boundaries*.
8. Technology Stack — *what it is built with: evaluated options and an ADR per decision*.
9. UX Specification — *what the user sees and does: every screen, workflow and state*.
10. Live Scoring Specification — *exactly how the engine processes each ball, deterministically*.
11. Offline-First Specification — *exactly how offline persistence and multi-device sync behave, deterministically*.
12. Data Specification — *the complete schema every other document's data ultimately lives in*.
13. API Specification — *the complete contract surface: every endpoint, traced to a requirement and a domain capability*.
14. Security Specification — *authentication through incident response, as requirements with acceptance criteria, grounded in a threat model*.
15. Testing Strategy — *how every requirement, every domain rule, and every architectural guarantee gets verified, before any code is written*.
16. Acceptance Criteria Catalog — *every approved feature as objective, checkable Given/When/Then*.
17. Repository Structure Specification — *the directory every section above will live in, once implementation is authorised*.
18. AI Context Pack — *the condensed rule-form version of all of the above, for every future AI coding session to load first*.
19. AI Development Harness — *the repeatable workflow that puts the Context Pack to work, task by task, and, post-release, the continuous loop that keeps it running*.
20. Implementation Task Backlog — *the Master Specification broken into the small, dependency-ordered units the harness actually runs*.
21. Adversarial Verification Report — *where the specification itself was stress-tested and found wanting, before any code could inherit the gap*.
22. Release Readiness Assessment — *the verdict: is any of this ready to ship, and what would have to be true first*.
23. Production Deployment Plan — *how it would actually reach production, and how to reverse it, once that verdict changes*.
